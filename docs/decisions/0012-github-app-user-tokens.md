# ADR 0012: github.com through the shared bot-bottle GitHub App's user tokens

- **Status:** Accepted (its deploy-key transport for git-gate is replaced by ADR 0014: HTTPS with the user's token, and no Administration permission)
- **Date:** 2026-11-02
- **Deciders:** didericis

## Context

git-gate pushes and fetches over a deploy key minted per launch on each
granted repo. GitHub support first minted them with a pasted personal access
token that had to hold Administration: read & write: a long-lived, broad
credential the operator makes by hand.

PRD 0112 (design repo) proposed a GitHub App per operator, minting
installation tokens with the app's private key, and PRD 0114 moved that
minting to the hosts. That puts an app's private key on every host, makes
each operator register an app, and attributes the work to a bot rather than
the operator. This record supersedes both on how GitHub is reached.

Checked against GitHub's documentation (2026-11-02):
- **Device flow needs no secret.** A user access token is requested with the
  client id alone (`POST /login/device/code`, then
  `POST /login/oauth/access_token` with `grant_type`
  `urn:ietf:params:oauth:grant-type:device_code`); the app must have device
  flow enabled.
- **Refreshing needs no secret for device-flow tokens.** The refresh request's
  `client_secret` is "required unless the user access token was generated
  using the device flow". An expiring token lasts eight hours; its refresh
  token six months, and it rotates on each refresh.
- **Deploy keys accept user access tokens:** `POST`/`DELETE
  /repos/{owner}/{repo}/keys` need the repository permission Administration:
  write, for user and installation tokens alike; `GET /repos/{owner}/{repo}`
  needs Metadata: read.
- **A user token is an intersection:** only permissions both the user and the
  app have, only repos the app is installed on that the user can reach.
- **An app's private key** is only needed to act as the app itself (its JWT,
  installation tokens). Keys are generated by hand after the app is made; once
  an app has one, GitHub won't delete the last, only rotate it.

## Decision

- **One shared GitHub App, `bot-bottle`,** owned by the `bot-bottle` org. A
  development environment uses its own app (`bot-bottle-dev`); hosts know an
  app by its slug and public client id only.
- **User access tokens only.** The operator installs the app on their accounts
  and orgs (one click, repos chosen on GitHub), then authorizes each host with
  the device flow. Work is attributed to the operator, "<user> via
  bot-bottle". bot-bottle never uses installation tokens.
- **No app key or client secret anywhere in bot-bottle.** Device-flow tokens
  are issued and renewed with the client id alone, on the host.
- **Expiring tokens are supported, and the default:** the host renews a token
  under a lock before it's used. When renewal fails (the refresh token expired
  or the operator revoked the authorization), cards and errors say to connect
  GitHub again.
- **Narrowing is ours.** The token reaches every installed repo the operator
  can; each run gets only a deploy key per granted repo, read-only unless
  `:write`, revoked at teardown. The token never enters a bottle.
- **A pasted personal token stays as a CLI fallback** (`--token`), for GitHub
  Enterprise Server and hosts that can't use the app.

## Consequences

- One-click setup per operator: install, then enter a code per host.
- The app's permissions are Administration: read & write and Metadata: read.
  Administration also lets a token change repo settings, so it's a broad
  permission held by the host, bounded by the installations and the
  operator's own access.
- A stolen host token acts as the operator on the installed repos until it
  expires (eight hours, or six months through its refresh token) or the
  operator revokes the authorization on GitHub.
- The org's app should never have a private key generated: user tokens don't
  need one, and a key could mint installation tokens for every installation.
  If one was generated, GitHub won't delete the last one, only rotate it, so
  it must stay offline and unused; bot-bottle has no code path that takes it.
- GitHub can't narrow a user token per repo for us; the per-run deploy key is
  the narrowing.
